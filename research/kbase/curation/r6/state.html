The Harness Already Knew

Round 5 wrote and ran every KBase parity transform, and handed forward a list rather than a clean tree. This page is that list, audited and then worked. The headline item was one line of engine code repeated in two hundred and fifty–nine places: a transform body had to declare one execution arm per runtime, and across the whole repository 121 of the 122 bodies that declared both passed the same command to each. The engine was already choosing. The author was being asked to restate the choice. Every thread below is now either fixed or decided, bar the two the last section names.

The arms, counted

Measured with the engine's own AST scanner over four transform roots, so this is what is in the tree rather than what the documentation claims. Every chain falls into exactly one of three states, and the middle bar is the whole argument: those bodies branch on the runtime and then hand both branches the identical string.

The 137 decompose further, and the decomposition is the reason the two-arm design felt necessary: 72 could gain a second arm mechanically, 44 pass mounts into the container, and 19 name an environment with no conda form at all. Under the collapse none of those three needs an author to say anything. The 72 simply work. The 44 already meet an assertion in GetContainerModel that reads “binds are meaningless without a container boundary” and names the runtime. The 19 already meet an assertion in ResolveEnvImage that names the file and the key it wanted. Both were written before the arms existed.

the one that actually differs

An image defect wearing a body's clothes

acquire/esm_c.py:85
  ifContainerDo   pip install --quiet huggingface_hub && python3 _acquire_esm_c.py
  ifVirtualEnvDo                                        python3 _acquire_esm_c.py

One chain in 259 gives its two arms genuinely different commands, and the difference is a package the container lacks and the conda environment has. That is not a portability decision the author needed a language for — it is a missing dependency, recorded in the wrong file. It gets fixed where it belongs, and then one command serves both routes.

Two types, one string apart

Two of the oldest threads look like they need something the language forbids. Round 3 wanted modelling::metabolic_model to extend a type in another file, and test_no_cross_file_extends refuses that; round 4 wanted the same for the bam types and did not try. But extends is only a build–time key–wise merge. Matching is pure property subsumption, and subsumption never needed extends at all. Each pair already agrees on everything except the one property that carries its prose.

What checking changed

Three items came off this list without being worked on, because reading the code said something different from what the journals said. Two of the three are cheaper than the fix they would have justified.

recorded reason · does not hold

No shipped template can see the transform the rule was protecting them from

The stated cost of joining bowtie2_bam to alignment::bam was that an RNA aligner would become a candidate producer for metabat2's bam requirement in a shipped template. All eleven shipped authors were read: not one names kbase in its A.transforms(...) list, and bowtie2_align lives nowhere else.

The ambiguity is real, but it lives only where both libraries are loaded together, which is the parity probe — and that gets re–solved either way. A second brake was already there and unremarked: bowtie2_align also requires a transcriptomics::experiment, so it cannot instantiate in a spec that declares none.

dangling requirement · by design, half

The producer is one transform from something already produced

binning::derep_mag_ref has been carried as “required by two transforms and produced by nothing” since round 3. Its own type comment says why: it is built once outside the DAG and handed to the driver as an input. So the dangling requirement is a design, not a defect — and the comment also says it is built from the is_centroid_95 rows of binning/cluster_table.tsv, which skani_dedup already produces.

Concatenate the representative bins with scaffold names namespaced by bin id, write the scaffold–to–genome table, build the index. Both consumers bind the result at a fixed mount and read three fixed filenames, so the product's shape is already specified by the code that reads it.

decided, not deferred

A bin is a mapping of contigs

Three tests assert that bin_fasta is not an assembly, and none of them says why — which is why rounds 3, 4 and 5 each re–raised it as an open question with 26 downstream requirements hanging on the answer. The answer is that annotation must not sit downstream of a bin, and the FASTA is a materialisation to be avoided where it can be.

That is a position, and it closes the thread. It goes beside the type and beside the tests, so the next round finds a reason where it currently finds three bare assertions.

Ninety environments, and the ones that cannot be reached

cobra.env is the only one of ninety with no container: line, and it says so in eleven lines of comment explaining that naming an unpushed image is worse than naming none. That is correct and it is also why the four modelling transforms run on exactly one host. Nine further environments name an image that an anonymous pull cannot see, and nothing in any of those files mentions it.

cobra · is there something to just use?

There is a published cobrapy image. It was tested, and it does not serve.

quay.io/biocontainers/cobra   newest tag 0.29.1   built 2024-12-03   216 MB
bioconda recipe               newest      0.21.0   (cobrapy moved to conda-forge)
docker/cobra/env.yml          pins        0.31.*   from conda-forge, verified at build

The image exists, is public, and is genuinely cobrapy despite sharing a name with an unrelated metagenomic assembler. Its LP solver returns the right objective. But it carries neither requests nor scipy, and lib::modelling fetches BiGG models with requests — so it was checked and rejected on evidence rather than on preference. Ours is pushed as quay.io/hallamlab/cobra:0.31.1, and all four modelling transforms re–run against it reproduce round 5's numbers exactly: 0.8739 on minimal glucose, infeasible with the carbon source shut, 95/72/137 for e_coli_core, and a gapfill from 0.0 to 0.639. The container: line is written and commented out for one reason only: quay creates a repository private, and naming an image the drawing host cannot see is the failure this round exists to stop.

nine images · 401 on an anonymous pull

Three of the nine were called unused. They are required by 21 transforms.

Six are lab images that a credentialed host pulls and nobody else does, and the fix is a dated comment above the container: line — the house style three files already use for a digest. One of those six names :latest, the only floating tag in ninety files, in a personal namespace rather than the lab's: two independent problems on one line. Six of the nine also carry no conda: line, which the preflight rewritten this round now refuses by name under MAMBA rather than at run.

The other three are ecspr_bake tags and they are 401 by design: synced to the cluster as SIFs and never pulled, so the URI is a name rather than a promise. They were also carried forward as required by no transform, and proposed for deletion on that basis. That count was taken over the standard library alone. Across src/fabfos/build_references they are required by 16, 4 and 1 transforms — the whole AAM and direction lanes. Nothing was deleted, and the lesson is the one this page keeps finding: the recorded reason is worth re–measuring.

What the round did not close

Two items, both found by doing the work rather than by planning it, and both left named rather than quietly absorbed.

solver · found while re–gating

A transform whose product extends the type it requires is a self–loop

seqkit_filter_contigs   requires assembly   produces filtered_assembly  (extends assembly)
polypolish              requires assembly   produces polished_assembly  (extends assembly)

Each satisfies its own requirement, so a plan wanting a filtered assembly can chain them arbitrarily deep. The parity analysis a4 solves through an eleven–long filter → polish → filter ladder before assembly_stats: nineteen steps where thirteen do the job, and every product in the ladder is consumed by the next, so it is a real chain and not dead branches. It was five long before this round; widening alignment::bam perturbed the search and lengthened it, which is how it was found. The language has no negation, so “an assembly not already filtered” cannot be stated as a requirement. That is a solver and modelling question, not a type one.

cobra · one click

The image is pushed. The repository is private.

Quay creates a new repository private, and the changevisibility API needs an OAuth token, which a docker push credential is not. So cobra.env carries the container: line commented out, with the URL, the one–line verification and the instruction — because naming an image the drawing host cannot see is precisely the failure the rewritten preflight now exists to catch, and shipping it to prove a point would be the worst possible way to demonstrate that.

Also standing: pathologic.env’s floating tag in a personal namespace; six environments with no conda: line, now refused by name at staging rather than at run; thirteen transforms still grouping on read_metadata that were not retrofitted onto the new sample name; and no transform body run under MAMBA since the arms were collapsed — every check here was under DOCKER, which is the same shape of gap the arms themselves were.
