# Cyanoverse annotation + GPR — resolved plan and where every input comes from

What the `annotation` driver actually resolves for a Cyanoverse-scale ORF
corpus, and the origin of each thing it reads. Generated by inspecting a
resolved plan, not by transcribing intent — every row below appeared in
`task.plan.given`.

Regenerate the plan and DAG with:

```bash
export PYTHONPATH="$PWD/src:$PWD/src/metasmith/src"
python -m fabfos.pipelines.annotation --orfs-dir <shards>/ --output <out> \
    --dag reports/dag/annotation_cyanoverse_sharded
```

## The plan

5 steps, independent of sample count — metasmith solves N samples as **one
unique case**, so the shape below is the same for 1 shard or 110.

```
orfs ─┬─ clean ──────────────┐
      ├─ proteinbert ────────┤
      ├─ diamond_uniref50 ───┼─→ gpr_4lane ─→ annotation::gpr_table
      └─ kofamscan ──────────┘
```

Rendered: `reports/dag/annotation_cyanoverse_sharded.svg`.

**Zero stubs.** All five references resolve to real DVC-pinned artifacts on a
worktree that has run `dvc checkout`; `report_stubs` prints nothing. This is a
change from when the driver's docstring and the README were written, both of
which claimed `reference_label_pool` was unavailable.

## Reference databases

| `ref::` input | Artifact | Size | Built from |
|---|---|---|---|
| `kofamscan_profiles` + `kofamscan_ko_list` | `data/processed/kofam_ref/` | 7.6 GB, 27,757 files | `data/originals/kofam/2026-06-30` (1.6 GB) |
| `uniref50_diamond_db` | `data/processed/uniref50_dmnd/uniref50.dmnd` | 17.4 GB | `data/originals/uniref/2026_02` (8.8 GB) |
| `mnxr_lookup` | `data/processed/mnxr_lookup/mnxr_lookup.parquet` | 133 MB | `originals/metanetx/4.5` + `kegg/119.0` + `rhea/141` |
| `reference_label_pool` | `data/processed/reference_label_pool/pool/` | 458 MB, 3 files | `originals/swissprot/2026_02` + `mnxr_lookup` |

Per-artifact notes that change how a number should be read:

- **KOfam** — profiles and `ko_list` must come from *one* release directory.
  Pairing a `ko_list` with profiles from another build applies the wrong
  score threshold to every hit, silently.
- **`mnxr_lookup`** is **every lane's terminus, not a fourth lane**: kofam emits
  KOs, CLEAN emits ECs, DIAMOND and the ProteinBERT pool emit UniProt
  accessions, and this is the one table turning all four id spaces into
  reactions. 30,467,712 rows after dedup. Its KO→reaction edge is built from
  one bulk KEGG REST call rather than the deployed per-KO crawl, reaching
  **~6.5× the reactions the deployed build did** — so kofam-lane numbers are
  **not comparable to the archived ones**.
- **`reference_label_pool`** — Swiss-Prot 2026_02, ProteinBERT-embedded,
  labelled with MetaNetX ids through Rhea; 222,019 labelled accessions,
  512-dim. Swiss-Prot rather than UniRef50 because the bridge's `reviewed` cut
  *means* Swiss-Prot exactly, and drawing sequences from UniRef50 silently
  dropped any accession that was not its cluster representative.
  **It is not the deployed pool** (KEGG-derived, 54,005 seqs keyed on KEGG gene
  ids). The `pbert_transfer` lane's numbers therefore move, and must not be
  reported as reproducing the deployed lane.
- **CLEAN** has no reference artifact by design; `mnxr_lookup` is the whole of
  what the build owes it.

ProteinBERT's weights are baked into its image and pinned nowhere else, so the
pool and the query lane agree only because both go through
`external_proteinbert:2024.03.28`. A pool embedded by any other build is not
comparable to a query embedded by this one — cosine distance against a pool
from a different embedder is meaningless but not detectably so.

## The corpus

Source: Globus collection `2602486c-1e0f-47a0-be15-eec1b0ff0f96` (Projects),
`/Manuscripts/Science/2025-09-23_Cyanoverse/`.

- `v2/orfs_and_metabuli/sequences-open_reading_frames/` — **2,844** `<SRA_ID>.faa`,
  the driver's input.
- `v2/to_assembly/sequences-assembly/` — **2,844** `<SRA_ID>.fna`, 1:1 with them.

The older top-level `asms/` (2,229) and `cds.faa/` (2,229) trees are a
superseded v1 pass; `v2/` is the current one.

**Already staged on fir**, so no transfer is needed:

```
/project/rpp-shallam/phyberos/cyanoverse/data/orfs_and_metabuli/sequences-open_reading_frames/
```

2,844 `.faa`, 30.61 GB, staged 2026-07-09. Verified against the Globus source by
filename set: zero on either side that the other lacks. Note this is
`/project/rpp-shallam`, **not** `/scratch` — fir's `/scratch` was measured
dropping 14 of 300 files in a write probe while `/project/rpp-shallam` lost 0
(see `examples/benchmark_v3_on_hpc.py`). Staging a 2,844-file corpus to
`/scratch` would lose files, and lose them silently.

Size distribution is extremely skewed: median 2.4 MB, min 176 B, max 492 MB
(~200× the median). One assembly alone exceeds any reasonable per-shard target.

`cds.pbert/gtdb_r226_pbert/` is **not** a reference label pool despite the
name — it is genome-level (indexed by `acc2contig.bac.csv`) and carries no
MetaNetX labels, where the pool is per-protein and label-bearing. Do not
substitute it.

## Sharding

`examples/cyanoverse_reshard_orfs.py` pools the 2,844 per-assembly fastas into
shards, prefixing every header `>{sample}::{original}` and writing a manifest.
The prefix is load-bearing: independent assemblies emit identical ORF ids
(`k141_1_1`), so pooling without it makes rows *collide*, and the collision
looks like a normal table.

Default target is 100,000 ORFs per shard, reasoned from the one prior real GPR
run (183 fosmid inserts → a single ~69k-ORF shard, one job).

Corpus scale, from the staged bytes rather than a guess: 30.61 GB at ~517 B/ORF
(calibrated on the three pinned E. coli proteomes; an over-estimate of record
size, since prodigal headers are shorter than NCBI's) is **~59 million ORFs**.

| ORFs/shard | shards |
|---|---|
| 100,000 (default) | ~590 |
| 250,000 | ~240 |
| 500,000 | ~120 |

**Neither the size nor the resulting wall-clock has been measured** — nothing has
been timed against UniRef50 at this shape. `--dry-run` reports the true packing
from actual record counts and should be run before committing to a count.
