One Frozen
Reference

Antonio's vOTU pipeline is a chain: every curation step writes a smaller FASTA, and every later tool reads whatever the previous filter left. Ported as-is, moving any threshold means re-running everything below it. So it is not being ported as-is. Three viral callers are reconciled into one candidate set, that set is frozen, and nothing after it writes sequence. Every tool downstream emits a table keyed on its contig ids — and the four filter scripts become a join you run afterwards.

Five passes

The plan, read one concern at a time.

Fourteen targets solve to 53 steps, nothing dropped, in about a second — and to one column of graph fifty-three steps deep, which is honest and nearly unreadable. These are five views of that single solve: same step numbers, same nodes, each keeping one part of the workflow and dropping the rest, so a step cut off from its neighbours simply becomes a root. A step that serves two concerns appears in both. Read them in order and you have walked the whole pipeline.

The pictures are metasmith's, not mine. Triangles are transforms, hollow circles the data they produce, filled circles the targets the driver names. Rows are dependency depth, and the number on a transform is its place in the plan's execution order — metasmith's numbering, which is not Antonio's numbering in the ledger below. lib, containers and env are hidden; the reference downloads are not, which is why four of the five views open on a database fetch.

a transform — one step data it produces a named target

Two properties of the graph shape every view. Its data nodes are types, not files, so sequences::orfs is a single node with two producers and the two chunker steps that follow it cannot be told apart from inside the graph — each view keeps the one that belongs to its story. And colour is metasmith's module scheme, which tints the subtree the rest of the graph can only reach through one step; it is recomputed per view, so a hue means nothing from one picture to the next.

Pass 1Spine25 nodes · short reads to bins

Short reads in, bins out, and nothing else. bbduk trims, megahit assembles, one mapping pass produces the coverage and the BAM the binners need, three binners run over the same contigs, CheckM2 scores each set, the aggregator keeps the best copy of every genome and skANI dereplicates what is left.

This is the metagenomics template the library already ships, unchanged. Everything in the next four passes hangs off the same megahit_assembly and touches none of it — which is the point: the viral work is an offshoot of this pipeline, not a second one.

Pass 2Viral classification22 nodes · contigs to a frozen set to vOTUs

Contigs are batched, and three callers read the batches. Each reduces its own output to a normalised interval table — one row per called interval, in the original contig's coordinates — which is the whole substance of the merge, because the three disagree on naming conventions and on nothing else that matters.

The merge deduplicates, unions overlapping intervals from earliest start to latest end, writes the provenance table recording who called what, and emits one dereplicated_candidate_virus. That set is frozen. The three steps below it — the two MMseqs2 clusterings that define a vOTU, and the length table — read it and write tables. Nothing after the merge writes a FASTA.

Pass 3Functional annotation39 nodes · four lanes, one gene table

prodigal calls genes on the contigs; the ORFs are chunked, the annotators run over the chunks in parallel, and the per-chunk tables are merged back. Four of them are the chosen four — KOfamScan, CLEAN, DIAMOND against UniRef50, and ProteinBERT embeddings — and gpr_4lane folds all four, with the MetaNetX bridge and the label-transfer landmarks, into one gene-attributed annotation::gpr_table.

That table is the target, and it is more than Antonio asked for: his step 25 wants KOfamScan alone, while the GPR table is this workspace's own gene-evidence format and the other three lanes arrive with it. Naming it is what pulls the entire panel in: four annotators, four merges, two reference downloads and two study-wide references, from one slot instead of four. DRAM rides the same ORF chunks and is the fifth annotator in the picture — it is Antonio's step 24, not one of the four.

Pass 4Viral annotation66 nodes · everything about a viral contig

The widest pass, and the one the freeze exists for. CheckV, prodigal-gv and a second KOfamScan run on the frozen set. DRAM-v cannot: it needs VirSorter2's affi-contigs file, so it runs per sample on the contig batches, which is why VirSorter2 reappears here feeding it. The callers' own annotation products — VIBRANT's AMGs and lifestyle table, VirSorter2's boundaries and scores, geNomad's virus and plasmid summaries — are per-contig, and they reach a vOTU through the provenance table rather than by being recomputed.

Host prediction is the reason the MAG lane is in this template at all, and it arrives by two independent routes. Bins go to GTDB-Tk and then into iPHoP's database, which is queried with the frozen set. Bins also go to CCTyper, whose CRISPR spacers are BLASTed against the frozen set directly. One is a model's opinion; the other is physical evidence of a past infection in this very dataset.

One thing to fix here. GTDB-Tk runs on SemiBin2's bins only — a single target reaches it, so the planner needed one instance — while iphop_add_to_db collects the aggregator's whole quality pool. Bins that MetaBAT2 or COMEBin contributed will join to no taxonomy at all.

Pass 5Taxonomy22 nodes · three of the four levels

Who is here, asked separately of each kind of object. Metabuli classifies the contigs against GTDB r232; geNomad emits a viral taxonomy for the calls it makes; vConTACT3 places the frozen set in a genome network; GTDB-Tk classifies the bins against the same r232 release, which is what lets a bin-level and a contig-level answer be compared without a crosswalk.

Reads are missing. Nothing in this plan classifies reads — the shipped metagenomics template names phyloFlash for exactly that and this driver does not. If read-level composition matters for the comparison, it is one target away, and it is the only one of the four levels this plan does not answer.

Why freeze

Set-dependence only bites if the set moves.

What the freeze buys

  • Thresholds move for free. The gene filter, the mobile-element filter, the 1 / 5 / 10 kb cuts and the vOTU slice are all a groupby over tables that already exist. A different cut costs a join, not a re-annotation.
  • The expensive tools run once. vConTACT3 has no way to reuse protein clusters on a subset — verified against the package, not the docs — so running it once on a fixed input is the only sane shape.
  • CheckV stops being a filter. It calls its own genes and its own HMMs, needs no prior viral call, and never drops anything: with no host boundary found it copies the contig through verbatim. Its contamination.tsv carries region_coords_bp, so the trim is a coordinate, not a cut.
  • One CheckV run, not two. end_to_end is contamination → completeness → complete_genomes → quality_summary over one shared prodigal-gv and DIAMOND pass. Steps 9 and 14 collapse into it.

What it costs, honestly

  • Every tool sees everything. With no size cut in the DAG, contigs Antonio would have thrown away at step 5 are still annotated. VirSorter2 over the full candidate set is the single most expensive item in the fan.
  • A sweep still is not a runtime knob. context.params is populated only from the Nextflow step metadata — cpus, memory, attempt — so existing params.get("min_length", …) calls in the library always take their defaults. Re-running the join outside the DAG is the sweep.
  • Abundance is derived, not re-mapped. Dropping CoverM means vOTU abundance comes from per-sample contig depth joined through the cluster table — the same logic bin depth already uses. A sample whose assembly missed a contig contributes zero for it, where cross-mapping would have counted its reads.
  • MetaPop is the one open question. It needs a directory of BAMs against one common assembly; the library's BAMs are per-sample against their own. Cross-sample microdiversity needs a mapping pass that nothing else in this design needs.
  • An annotation is computed on the parent contig, not the trimmed interval. The four per-contig annotators run per sample, so a provirus is annotated in the context of the host contig it sits in. For Antonio's gene-content rule that is the better input — the host genes it counts are on the untrimmed contig — but it is a real difference from running them on a curated vOTU set, and it will show in the comparison.
  • The freeze has to be one-way in the type system, not just on the page. Lineage constraints here are ancestral: the frozen set descends from every contig batch that fed the merge, so any requirement the frozen set also satisfies makes a caller's output eligible to feed the merge that produced it. The planner rejects the cycle, but it pays to find it, and not linearly — measured on this target set, with geNomad reachable on the frozen set the solve took 43 s; with VIBRANT reachable there as well it stopped finding any complete plan, returning zero steps in four seconds. That is why the annotators name sequences::contig_batch and every consumer of the frozen set names viromics::dereplicated_candidate_virus outright. An earlier draft of this design introduced a shared contig contract both satisfied; it is exactly the shape that reopens the cycle.

The three callers disagree on convention — geNomad appends |provirus_S_E, VirSorter2 ||full, VIBRANT _fragment_N, and CheckV adds _1 to a trimmed provirus. Reducing all four to one contig id and one interval is the whole substance of the merge.

Where this came from

A spreadsheet, fifteen shell scripts, and one Slack answer about thresholds.

The thresholds are not tuned. Asked in Slack on 16 June for a justification, Antonio answered that he followed the methods of one Nature Communications paper and that all of the thresholds were adopted from there. A corroborating detail: step 8's length ≥ 1000 is a no-op, because step 5 already cut at 1 kb — the signature of rules copied from a methods section rather than fitted to the data. Nothing on record shows hand-curation; “manually” meant submitting fifteen SLURM scripts one at a time.
