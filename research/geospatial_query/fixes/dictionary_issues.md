# Dictionary pass on geoquery 0.26.3: issues found while sourcing

## Purpose & Contents

Problems the five sourcing workers noticed while rebuilding feature_descriptions.csv and class_descriptions.csv. Unverified leads, one file section per slice.

## bio_health_socio


## Definitions that could not be sourced
- statcan_* Census Profile fields: www12.statcan.gc.ca (the 2021 Census Dictionary) answers HTTP 403 to every fetch. Definitions for private dwellings, occupied dwellings, value of dwellings and the carried household, tenure and income quotes come from the 2016 dictionary (https://cdn.dal.ca/content/dam/dalhousie/pdf/library/gis/2016%20Census%20of%20Population_Dictionary.pdf), flagged in `note`. statcan_population has no definition at all. The SDMX code list (https://api.statcan.gc.ca/census-recensement/profile/sdmx/rest/dataflow/STC_CP/DF_DA/latest?references=all&detail=full) gives characteristic labels only.
- phacww_* : the published dictionary https://health-infobase.canada.ca/src/data/covidLive/wastewater/covid19-wastewater-data-dictionary-en.csv lists a different column set (w_avg, weekstart, measureID, Grouping...) from the CSV the adapter reads (Date, Location, region, measureid, fractionid, viral_load, seven_day_rolling_avg, pruid; adapters_health_env.py:820-856). Date, Location, viral_load and the fractionid values liquid/solid have no definition. The 7-day rolling average definition exists only in the dashboard page's JSON-LD FAQ markup (https://health-infobase.canada.ca/covid-19/wastewater/).
- The unit copies/mL for phacww_viral_load and phacww_seven_day_rolling_avg is set by geoquery (adapters_health_env.py:853); no PHAC page states a unit.
- rvdss_jurisdiction: the dictionary's 'Jurisdiction' means 'Reporting country' (value Canada); the CSV column read is `province` (adapters_health_env.py:763), which the dictionary does not list (https://health-infobase.canada.ca/src/data/respiratory-virus-detections/download/Data_Dictionary.xlsx).
- NRCan landcover (14 classes) and AAFC ACI (14 of 24 classes): the published lists give names only. NRCan's class index (https://datacube-prod-data-public.s3.ca-central-1.amazonaws.com/store/land/landcover/ClassIndex_v2.pdf) has names, codes and colours; AAFC's ISO 19131 specification describes only ten classes.
- wd_entities_by_class: 'ditch', 'urban-type settlement' and 'pond' cannot be tied to one Wikidata item because geoquery keeps the label and drops the Qid (adapters_infrastructure.py:665); 'ditch' matches three items, 'urban-type settlement' two, 'pond' none by exact label.
- ENA geo_box1 (https://www.ebi.ac.uk/ena/portal/api/doc is a Google Doc shell; text read from its export link) and MGnify: no definition of the counted quantity; ENA's filter function is quoted in `note`.

## Misleading names, wrong units, odd values
- ghs_smod class 21: GHSL's level-2 list prints "Suburban or per-urban grid cell" (typo, https://ghsl.jrc.ec.europa.eu/documents/GHSL_Data_Package_2023.pdf section 2.6.2); Table 21 and geoquery (adapters_census.py:757-759) use "Suburban or peri-urban grid cell".
- ghssmod_group_frac: level 1 omits water, so the three classes sum to 1 minus the water share (adapters_census.py:818-820); GHSL's own level-1 raster has no water class either.
- statcan_median_household_income_approx, statcan_median_dwelling_value_approx, statcan_avg_dwelling_value_approx: weighted means of DA medians or averages (adapters_census.py:190-196); the name says "approx" but a mean of medians is not a median.
- statcan_population, statcan_private_dwellings and the household counts are fractional (example 70392.2) because DAs are apportioned by area share; SI_unit count suggests integers.
- statcan_popest example 81611 and statcan_population example 70392.2 describe the same CSD but the first is a 2025-era estimate and the second the 2021 census apportioned to the AOI; the pair is not comparable without the reference period (adapters_census.py:608-649).
- statcan_csd_type example 'SM' is a 3-character code; the carried quote speaks of 53 types, while the 17-10-0155 cube footnote says 57.
- hansen_loss_n_years_affected: SI_unit is count but the example 25.0 and hansen_px_sampled 71360.0 are floats though the code returns int (adapters_physical.py:206,225). hansen_loss_modal_year and hansen_loss_last_year are absent, not 0, when the AOI has no loss (adapters_physical.py:221-226), so a missing row is not a missing measurement.
- Hansen's v1.13 page says lossyear is "a value in the range 1-20" next to "2001-2025" (https://storage.googleapis.com/earthenginepartners-hansen/GFC-2025-v1.13/download.html); the carried quote repeats that inconsistency.
- hansen_gain_frac_2000_2012 covers a different period from hansen_loss_frac_2001_2025.
- modis_n_composites example 23.0 is a float (pipeline.py:412 returns int). modis_ndvi_amplitude is the spread of AOI-mean composites of one tile over the last 365 days, not a seasonal amplitude (pipeline.py:393-414). The carried quote defines NDVI as a product layer, not the mean over composites.
- iolulc_n_classes counts Clouds and iolulc_frac includes Clouds in the denominator (adapters_census.py:849-857). The Esri item page (https://www.arcgis.com/home/item.html?id=cfcb7609de5f478eb7666240902d4d3d) lists years through 2025 while the PC collection says 2017-2023.
- nrcanlc_*: the adapter reads NRCan's datacube asset 'classification' (pipeline.py:301), but earlier dictionaries named PC's asset 'landcover'. PC's own 2015 labels differ from NRCan's (Barren lands, Urban, Snow and Ice).
- aafc_aci_frac class 'Corn for grain' is the CSV label for code 147; the ISO 19131 spec names it 'Corn' (https://agriculture.canada.ca/atlas/data_donnees/annualCropInventory/supportdocument_documentdesupport/en/ISO%2019131_AAFC_Annual_Crop_Inventory_Data_Product_Specifications.pdf). The CSV label 'Forest fire/burnt area ' has a trailing space that the adapter strips on read (pipeline.py:325).
- ESA WorldCover: class 95 Mangroves is a published class with no row in the classes file (none in the mined AOIs), so a dictionary built from the file alone is incomplete against the 11-class legend.
- rvdss_*: the dictionary spells 'positivie' and its first sheet names COVID-19 where the data says SARS-CoV-2. rvdss_tests is identical for Influenza, Influenza A and Influenza B (9061), so the three tests rows are one count reported three times.
- phacww_date and phacww_location use the class column for liquid/solid but are not per-class measures; phacww_seven_day_rolling_avg and phacww_viral_load have identical example values (1.65 and 0.5581) because the first sample's rolling average equals its load. 'Campbellton (NML Historical Data)' as a Location reflects a separate NML series at one coordinate (adapters_health_env.py:843).
- odhf_nearest_facility_name example is lower case ('fort mcmurray community cancer centre') while the type is Hospitals; ODHF keeps source spellings. Two rows spell a type in lower case and are mapped (adapters_census.py:260-262). Distances are from the AOI centroid, not the AOI polygon (adapters_census.py:979-986).
- gbif_*: counts now use the AOI polygon (WKT) and page the speciesKey facet; the previous 1200 cap no longer applies (pipeline.py:458-472).
- wd_entities_by_class: lists only the five most frequent classes per AOI (adapters_infrastructure.py:662-666) so a missing class does not mean zero; a label shared by two classes becomes 'label (Qid)'. Class 'Wikimedia duplicated page' (Q17362920) shows duplicate items are counted as entities.

## geo_climate_water


- clim_mean_annual_temp_c: the carried quote ("Air temperature at 2 meters above ground...") defines hourly `temperature_2m`. The Open-Meteo page (https://open-meteo.com/en/docs/historical-weather-api) gives the daily `temperature_2m_mean` only the label "Mean Temperature (2 m)". Definition left blank. The name also reads as a long-term climate normal; it is the mean of 10 years of daily means (pipeline.py:549-565).
- clim_daily_mean_temp_min_c / _max_c: the extreme of daily means, not of any observed daily extreme. The name says so, but the "min/max temperature" reading is easy to make.
- clim_annual_precip_mm: annualised by dividing by non-null days/365.25 (pipeline.py:564), so it differs from a calendar-year total.
- jrc_gsw water_occurrence_pct_*: the previous quote came from the 2021 Data Users Guide ("March 1984 to December 2021"), but the data is jrc-gsw v1.3 covering 1984-2020 (versions.csv). Replaced with the Planetary Computer STAC wording (https://planetarycomputer.microsoft.com/api/stac/v1/collections/jrc-gsw). Note too that obs_date was changed to 1984-03-01/2020-12-31 in fixes/core.md.
- etopo_bed_elev_m_*: the carried quote (from the ETOPO user guide) defines the horizontal and vertical reference of the tiles, not the elevation value itself. Kept per the carry rule.
- cop_dem_glo30 elev_m_*: the carried quote says the product is a Digital Surface Model, so the values are canopy and building tops; the feature name `elev_m` does not say so. The Planetary Computer `data` asset has no description of its own.
- mrdem_30: dtm values are referenced to CGVD2013 (product specification PDF p.11 and 2.8.1); ETOPO is referenced to EGM2008 (per the carried quote). The DEM sources are therefore not on one vertical datum.
- *_n_px (elev_m_n_px, etopo_bed_elev_m_n_px, mrdem_dtm_elev_m_n_px, water_occurrence_pct_n_px): count pixels of the decimated read (MAXPIX 320 in pipeline.py:30, 128 for ETOPO at adapters_physical.py:525), not native-resolution pixels. The name does not say so (fixes/physical.md section 6 notes this).
- geo_t_int_age_ma / geo_b_int_age_ma: the Macrostrat API states no unit; Ma is geoquery's assumption (fixes/core.md line 160). The values are interval bounds (top age of the interval containing the unit's top boundary), not unit ages.
- geo_* (macrostrat): only the first unit returned is used; the API sorts by largest map scale, which is geoquery's reliance on undocumented ordering (pipeline.py:432).
- gsc_surf_frac_in_aoi classes: the published legend (https://maps-cartes.services.geo.ca/server_serveur/rest/services/NRCan/gsc_surficial_geology_en/MapServer/3) holds names only; the same name recurs under several codes (Littoral and nearshore sediments under GLn, GMn, Ln, Mn; Offshore sediments under GLo, GMo, Lo, Mo). The per-class prose lives in the data's `description_en` field, not in a published legend. The legend entry for V ends with a stray full stop.
- nrcanpf_*_frac_in_aoi classes: the REST layer (https://maps-cartes.services.geo.ca/server_serveur/rest/services/NRCan/permafrost_atlas_of_canada_en/MapServer/6) publishes no class descriptions. Class names are as published, including "Medium to low (20% to <10%)" (reversed range) and "Sporadic discontinuous permafrost (10 % to 50%)" (inconsistent spacing).
- nrcanpf_zone_frac_in_aoi includes the "No permafrost (0%)" class, while nrcanpf_frac_in_aoi, nrcanpf_nearest_km and nrcanpf_present_in_aoi exclude it (adapters_physical.py:497-507). The `nrcanpf_` prefix on nearest/present/count therefore means "permafrost polygons", not "all atlas polygons".
- The example values for the class rows (e.g. Continuous permafrost 1.0 and Sporadic 1.0) come from different AOIs; they do not sum to 1 within one AOI.
- ne_glaciated_*: Natural Earth documents the layer only; its page (https://www.naturalearthdata.com/downloads/10m-physical-vectors/10m-glaciated-areas/) lists no fields. It warns the DCW-derived extents are decades old ("collected decades ago").
- noaa_nsidc_sic_cdr: nsidc_sic_ge15pct_present (not in this slice's examples) uses a 0.15 threshold that is geoquery's. The V6 user guide (https://nsidc.org/sites/default/files/documents/user-guide/g02202-v006-userguide.pdf, p.7) defines cdr_seaice_conc as "the fraction of ocean area covered by sea ice", valid range 0 to 100 scaled by 0.01, fill 255; only the concentration features (absent from this slice) could carry it. The four features here are grid-geometry counts with no upstream field.

## hazards


- `naps_annual_mean` carries SI_unit `ppb` in the input, but the Means file header (https://data-donnees.az.ec.gc.ca/api/file?path=air%2Fmonitor%2Fnational-air-pollution-surveillance-naps-program%2FData-Donnees%2F2024%2FContinuousData-DonneesContinu%2FAnnualSummaries-SommairesAnnuels%2F2024_Means_EN.csv) gives CO in ppm and PM10/PM2.5 in ug/m3. Unit is per record (geoquery/adapters_health_env.py:267, :284-285).
- `cams_hourly_mean_30d` and `cams_hourly_p95_30d` carry SI_unit `ug/m3`, but class `aerosol_optical_depth` is Dimensionless per https://open-meteo.com/en/docs/air-quality-api (the adapter writes unit "1", adapters_health_env.py:382).
- `npri_*_releases_25km` carry SI_unit `kg`, but class `Dioxins and furans - total` is in g TEQ (adapters_health_env.py:408, 432; seen in hazards/eccc_npri.csv). Unit is per record.
- NPRI classes overlap: "Benzene" and "Speciated VOC - Benzene", "Xylene (all isomers)" and "Speciated VOC - Xylene (all isomers)", "Volatile Organic Compounds (total)" and the speciated rows, "Total Particulate Matter" and PM10/PM2.5. Class values are the file's substance names verbatim, but summing across classes double counts (https://www.canada.ca/en/environment-climate-change/services/national-pollutant-release-inventory/substances-list.html publishes names only).
- NPRI releases use the "Air Emissions - Total" column, which excludes road dust (fixes/health_env.md, L29). The carried quote defines "releases" generally and does not say this.
- `NPRI_MEDIA` key "Rejets au sol - Totalee / Land Releases - Total" (adapters_health_env.py:404) has a doubled "e" in "Totalee". Presumably the source header spells it so (the adapter ran); I did not verify against the CSV.
- `ghgrp_max_facility_co2e_excl_co2bio_kt_25km` and `ghgrp_co2e_excl_co2bio_kt_25km` have carried quotes that describe the CO2bio exclusion and GWP basis, not the column itself; ECCC publishes no per-column definition I could find. The source column is in tonnes, output is kt (adapters_health_env.py:510, 512).
- `ghgrp_facilities_25km` counts rows of the newest reference year (adapters_health_env.py:509), not distinct facilities; a facility with several rows would count more than once.
- `fcsi_*` definitions: the live host https://www.tbs-sct.gc.ca/fcsi-rscf/oddo/fcsi-rscf-eng.rtf returned "Request Rejected" to automated clients (and WebFetch), so newly sourced FCSI quotes were read from the Wayback snapshot https://web.archive.org/web/2023/https://www.tbs-sct.gc.ca/fcsi-rscf/oddo/fcsi-rscf-eng.rtf. Carried FCSI quotes were not refetched.
- FCSI classification and status values are not listed in the data dictionary; "High Priority for Action" etc. (adapters_health_env.py:655) are taken from the XML via the lane report (fixes/health_env.md section 3), so their match to a published list is unverified. Class definitions are therefore blank.
- `fcsi_contamination_volume_m3_25km` and `fcsi_contaminated_area_ha_25km` sum estimates that the dictionary says are "recorded at the site ... at the time of assessment"; absent estimates are counted as 0 (adapters_health_env.py:657-658), so 0 can mean "not reported".
- `eq_count_100km_m2.5`: the previous dictionary row described `len(features)`; the code now reads the count endpoint (pipeline.py:446-448). The name hides the 1980-01-01 start (pipeline.py:444), and the radius is from the AOI centroid, unlike the polygon-based distances elsewhere in this family.
- `eq_max_mag_100km` mixes magnitude types (preferred magnitude per event; fixes/core.md:18). The carried quote defines `mag` correctly for that.
- NAPS station counts (`naps_continuous_stations_*`) count only stations in the annual Means report, not the NAPS station list (https://data-donnees.az.ec.gc.ca/api/file?path=air%2Fmonitor%2Fnational-air-pollution-surveillance-naps-program%2FProgramInformation-InformationProgramme%2FStationsNAPS-StationsSNPA.csv).
- NAPS `Average` has no definition beyond the file header's reporting criteria, which I used as the definition. The "NAPS ID" and "City" columns have none.

## infrastructure

- nrcan_900a: no field-level data dictionary reachable for NAME_E / PRD_DESC_E (https://open.canada.ca/data/en/dataset/000183ed-8864-42f0-ae43-c4313a860720 has a dataset description only; the PDF guide directory https://ftp.maps.canada.ca/pub/nrcan_rncan/Mining-industry_Industrie-miniere/900A_and_top_100/PDF/EN/ was not read). All six nrcan900a rows left blank.
- Four previous quotes were OSM wiki tag definitions attached to Overture class values (ovt_generator_n, ovt_power_plant_n, ovt_pipeline_km; prev from ovt_power_plant_n etc.); they define an OSM tag, not the Overture field, so they were replaced with the Overture infrastructure_class intro (https://docs.overturemaps.org/schema/reference/base/types/infrastructure_class/), which describes the field only.
- Overture class pages publish names only for infrastructure_class, land_use_class and building_class (https://docs.overturemaps.org/schema/reference/base/types/infrastructure_class/, .../land_use_class/, .../buildings/types/building_class/); road_class describes 4 of the 16 values seen, rail_class 1 of the 2 seen. Most class rows are blank.
- ovt_rail_km_by_class example classes disagree with the total: standard_gauge 11.119 + unknown 11.918 = 23.04 km, but ovt_rail_km example is 11.918. Either the class examples come from different AOIs or lengths are double counted. Check geoquery/adapters_infrastructure.py:347 and 332-352.
- ovt_road_km_by_class: the input example_value (89.38) is the cycleway row, not a total; same pattern for other *_by_class examples.
- gppd_median_commission_year_50km: carried Earth Engine quote says "weighted by unit-capacity when data is available" but the code takes a plain median of commissioning_year (geoquery/adapters_infrastructure.py:459). Input unit "yr" reads as a duration; value is a calendar year.
- GPPD definitions are quoted from the Google Earth Engine catalogue (https://developers.google.com/earth-engine/datasets/catalog/WRI_GPPD_power_plants), not WRI. WRI's pages (https://github.com/wri/global-power-plant-database, https://datasets.wri.org/dataset/globalpowerplantdatabase) define only primary fuel. Earth Engine may describe a different release than the pinned v1.3.0 CSV. Not refetched.
- Carried Overture building height quote ("This is the distance from the lowest point to the highest point.") was not re-verified: the current building page fetch showed only "Height of the building or part in meters."
- ovt_power_plant_names reads names.primary; the Overture infrastructure page describes the 'names' field as "All known names by which the feature is called". Primary-name definition comes from https://docs.overturemaps.org/schema/reference/common/names/ (carried).
- ovt_region_code: previous unit "count" is wrong (ISO code string); input already blank.
- Sources epa_echo duplicated across adapters (lane report section 6) is outside this slice.
- ovt_division_n_in_aoi: carried "Divisions are recognized..." defines the feature, not the row-count; fine as the counted object, but ovt_division_n_in_radius counts points inside the buffered AOI, not a radius from a centre (geoquery/adapters_infrastructure.py:698).
- ovt_address_street_density counts distinct street names per km2, not street length; the name suggests length density (geoquery/adapters_infrastructure.py:540).
- Class values: all seen values appear on the published lists (checked infrastructure, land_use, building, road, rail pages); gppd fuel values come from the CSV itself, no published list.
- Division subtype quotes for macrohood and neighborhood were assembled from adjacent fragments of the fetched page.

## latent_spectral

- Class files in2/latent_classes.tsv and in2/spectral_classes.tsv hold a header only; no class rows to write.
- clay_emb_patch_count and clay_emb_patch_l2_norm_mean / clay_emb_mean_cos_to_tile_patch_mean: geoquery "patch" means a table row (a 512x512 chip, adapters_physical.py:355-358), but Clay uses "patch" for the 16x16 sub-patches inside a row (https://clay-foundation.github.io/model/clay-v0/model_embeddings.html). Misleading name.
- clay_emb_* definitions: the only upstream text is the embeddings column description; the features are geoquery statistics of it, so each row's note says the quote defines the input.
- aef_emb_a00..a63: carried quote defines the 64-band embedding collectively (the GEE page says bands "are not independently interpretable"); the AOI mean vector is not unit length (aef_emb_mean_vector_l2_norm example 0.889), contrary to a casual reading of "unit-length".
- palsar_*_db_*: the only upstream text (also the PC asset description) defines the 16-bit DN, while the feature is dB computed with a calibration factor (pipeline.py:376-380); no fetched page documents DN-to-dB or CF. Same for s1_vv_db_mean (quote defines linear gamma0; pipeline.py:391).
- s2_eo_cloud_cover_pct: definition is from the STAC EO extension (raw.githubusercontent.com/stac-extensions/eo/main/README.md), not the PC collection page; it is scene-level cloud cover, not over the AOI.
- s2_red_reflect_mean and s2sig_raw_b*: carried quote is the band title "Band N - ..."; the PC collection now titles them "Band 4 - Red - 10m" etc. A title, not a definition of a reflectance statistic.
- s2sig_* features carry the aef/embedding-style names but are not learned embeddings (adapters_s2signature.py:3-12); the file's own docstring says it must never be labelled as one.
- aef_emb_tile_crs / aef_emb_tile_path: no data dictionary for aef_index.parquet was fetched; left blank.
- s2_ndvi_n_px / s2_ndwi_n_px count decimated, unmasked pixels (pipeline.py:128-135), not native 10 m pixels.
