# Feature dictionary: issues found while sourcing definitions (2026-11-27)

Raised by the sourcing subagents while reading the adapters against upstream docs. Unverified leads, not confirmed bugs.

Dispositions of every lead below, the units and class lists applied, and the live test results are in `fixes/<lane>.md` (core = pipeline.py, s2signature, embeddings).

## geo_climate_water


- gsc_surficial_1880a: the adapter downloads `.../Surficial-geology_Geologie-des-depots-meubles/surficial_geology_index_geologie_surface/gsc_surficial_geology.gdb.zip` (adapters_physical.py:83-84), which open.canada.ca lists under "Surficial geology index map" (dataset cebc283f-bae1-4eae-a91f-a26480cd4e4a), not under "Surficial geology map of Canada, 1:5 000 000" (317ebf06-e053-b10f-6092-bfe0c1af8703, a different ftp path). The source id, docstring and obs_date all say Map 1880A (adapters_physical.py:547,563). Confirm which dataset the file really is before sending the name to the collaborator.
- gsc_surf_*: the only upstream documentation found is ArcGIS field aliases ("Geology category", "Label", "Description"; REST layer .../gsc_surficial_geology_en/MapServer/3). No prose dictionary was found. Same for nrcanpf_zone_class / ice_class / zone_code (aliases "Permafrost extent", "Ground ice", "Permafrost class"; .../permafrost_atlas_of_canada_en/MapServer/6).
- clim_coldest_day_c and clim_hottest_day_c are min and max of the daily MEAN temperature (temperature_2m_mean), not the coldest daily minimum or hottest daily maximum (pipeline.py:459,463-464). The names mislead.
- clim_annual_precip_mm divides the 10-year precipitation sum by a hard-coded 10 (pipeline.py:465); the example clim_n_days 3653 implies 10 years, but a gap-filled or short series would be mis-scaled.
- Open-Meteo documents no `temperature_2m_mean` row (daily table lists only max/min, https://open-meteo.com/en/docs/historical-weather-api); the quoted definition is the hourly temperature_2m text plus the page's "simple 24 hour aggregation" sentence.
- Macrostrat t_age / b_age (pipeline.py:354) are not in the route's published fields list (only t_int_age / b_int_age, which are interval ages). Their definition and unit are undocumented; geo_age_*_ma assumes Ma. Also only the first unit of the response is used (pipeline.py:352), and geo_n_units counts all of them.
- slope_deg_*: pixel spacing is computed from the latitude extent only (111320 * dlat / rows, pipeline.py:224) and used for both axes, ignoring cos(latitude) on x. Example slope 0.47 deg at relief 276.8 m looks plausible but the x spacing is overstated at high latitude.
- usgs_namrad: adapter docstring cites Duval, Darnley & Garrett 1990 and obs_date "1960-1983 (NURE/GSC surveys, 2009 compilation)" (adapters_physical.py:594,621), but the USGS metadata (https://mrdata.usgs.gov/metadata/narad.txt) says NURE 1975-83, and the landing page cites Duval et al. 2005 (OFR 2005-1413). SI_unit for namrad_th_k_ratio and namrad_u_th_ratio is "1" but the ratio is ppm eTh per percent K, and ppm eU per ppm eTh; the first is not dimensionless.
- noaa_nsidc_sic_cdr: the user guide fetched is Version 4; the adapter takes the newest file in the NCEI access directory with no version pin (adapters_physical.py:369-390). nsidc_sic_frac_* are 0-1 fractions (guide: valid range 0 to 1), consistent with SI_unit 1. nsidc_sic_frac_* return 0.0 for both land-masked and truly ice-free cells; use nsidc_sic_valid_cells to tell them apart.
- etopo: the user guide describes 15 arc-second tiles; the adapter reads the 30 arc-second global file. Elevation reference is EGM2008, which the guide calls "an adequate approximation of mean sea level"; etopo_frac_below_sea_level and etopo_is_submarine test value < 0 on that basis. etopo_max_depth_m = 0.0 together with etopo_min_elev_m = 225.4 is expected (land AOI) but the feature is 0.0 for any AOI with no negative cell.
- mrdem_30: the adapter prefers asset `dtm`, falls back to `dsm`, then to the first asset (pipeline.py:341). The feature name does not say which; the quoted definition is for the DTM.
- natural_earth_10m: neglac_* are named for glaciers, but the dataset is "glaciated areas"; the only field documented is "Includes name attributes for major polar glaciers." neglac_nearest_name example "unnamed" is the adapter's own fallback (adapters_physical.py:436).
- Several features are geoquery-computed with no upstream counterpart and carry a blank definition: all *_n_px, relief_m, slope_deg_*, etopo_frac_below_sea_level, etopo_is_submarine, etopo_max_depth_m, gsc_surf_n_units_in_aoi, gsc_surf_dominant_frac, geo_n_units, neglac_* (except name), nrcanpf_* presence/count/fraction/distance, namrad ratios and pad, nsidc_sic_* (except frac_mean/max), clim_n_days, water_frac_ge50pct.


## hazards


- NPRI `npri_total_releases_kg_25km`, `npri_*_kg_25km` (adapters_health_env.py:472-488) sum every substance row. NPRI reports PM (total), PM10 and PM2.5 as separate substances, and the interpretation guide has an "Avoid double or triple counting > Particulate matter" section (https://www.canada.ca/en/environment-climate-change/services/national-pollutant-release-inventory/using-interpreting-data.html). The totals therefore count particulates up to three times and mix unlike substances.
- `npri_so2_kg_25km`, `npri_co_kg_25km`, `npri_nox_kg_25km`, `npri_pm10_kg_25km`, `npri_pm25_kg_25km` are air+water+land totals (adapters_health_env.py:473,480-488), though the names read as air-quality (air-only) quantities.
- `npri_top_substance_kg_25km` equals `npri_so2_kg_25km` in the example (47317022.3). Same field, whenever SO2 is the top substance.
- NPRI mass sums drop g TEQ rows (dioxins and furans) silently (adapters_health_env.py:468). The 'Air Emissions - Total' columns are not documented as excluding or including road dust; the guide says "Direct air releases of particulate matter include road dust emissions."
- NPRI file choice: `sorted(names)[-1]` (adapters_health_env.py:423) picks the latest year at run time. The ECCC listing now holds NPRI-INRP_DataDonnées_2025.csv, but the dataset example says 2024, so a re-run may differ from the shipped data.
- No field-level NPRI or GHGRP data dictionary exists. The NPRI xlsx Notes and Meta Data sheets, the open.canada.ca page and the GHGRP Read Me define no columns. NPRI rows carry concept-level quotes only; the canada.ca page blocked curl, so those quotes came through WebFetch and are not byte-verified.
- GHGRP `ghgrp_co2e_kt_25km` and `ghgrp_max_facility_co2e_kt` read 'Total Emissions (tonnes CO2e) ... - excl. CO2bio', so biogenic CO2 is excluded. Names do not say so. `ghgrp_max_facility_co2e_kt` also looks like it has a different scope from `ghgrp_co2e_kt_25km`: it is the max of a single facility, not a sum.
- GHGRP example: 4 facilities within 25 km total 21736.97 kt, with the largest at 13677.66 kt. Plausible, but the example has no unit check in the file; the file column is in tonnes and geoquery divides by 1000 (adapters_health_env.py:554-555).
- NAPS `naps_stations_25km/50km` and `naps_nearest_station_*` count only stations present in the continuous Means file (adapters_health_env.py:261-266), not every NAPS station (integrated or filter-based sites are missing). The names suggest the full network.
- NAPS `naps_*_ppb_mean`: the Means file header gives units (ppb; CO ppm; PM ug/m3), matching SI_unit. But 'Average' is only defined implicitly via the reporting criteria in the header (50% of hours valid, each quarter at least 2 valid months).
- NAPS `naps_nox_*` features come from the file's 'NOX' label (adapters_health_env.py:254); the header writes 'NOx'.
- NAPS `naps_nearest_station_id` is stored as str (adapters_health_env.py:263). The example 090805 keeps its leading zero, but the wide parquet holds text values, so leading zeros are fragile if cast.
- CAMS `res_m: 44000` (adapters_health_env.py:392) vs Open-Meteo docs "0.4° (~45 km)" for CAMS Global (https://open-meteo.com/en/docs/air-quality-api).
- CAMS: Open-Meteo calls the returned lat/lon "the center of the weather grid-cell" (shared wording across its APIs). `cams_grid_lat/lon` are that centre, not the AOI centroid.
- CAMS `cams_*_mean/p95` are over the 30 days before the run date (past_days=30, forecast_days=0, adapters_health_env.py:366-367), a 720-hour window (`cams_n_hours`), so they are not climatological and change with run date. The domain is cams_global, a model analysis/forecast, not measurements, though sources.tsv lists it as "blended".
- CAMS 'ozone', 'carbon_monoxide', 'nitrogen_dioxide' and 'sulphur_dioxide' share one Open-Meteo description ("Atmospheric gases close to surface (10 meter above ground)"); the page does not define each gas separately.
- FCSI `fcsi_contaminated_soil_m3_25km`: the dictionary field `CubicMetres` is "cubic meters of contamination", not soil specifically (adapters_health_env.py:771). Only the first ContaminationEstimates element per site is read (line 759), though the dictionary says multiple estimates can be reported.
- FCSI `fcsi_high_priority_sites_25km` counts Classification Code == "1" (adapters_health_env.py:802). The dictionary says only "the classification code value"; the 'high priority' meaning of code 1 is not documented there.
- FCSI dictionary names the identifier attribute `SiteIdentifier`; the adapter reads `FederalSiteIdentifier` (adapters_health_env.py:764). Either the dictionary or the XML differs. `site_id` is not exposed as a feature, so no output is affected.
- FCSI `fcsi_nearest_site_name` example "Mile 9.7 Athabasca River - Discarded batteries, Rear and" is cut at 56 characters mid-phrase (adapters_health_env.py:766,793). `fcsi_nearest_site_org` is cut to 8 characters (line 795), though codes are 3 characters.
- FCSI active/closed counts ignore 'Suspected' sites (a third status in the dictionary), so active + closed need not equal `fcsi_sites_25km`.
- USGS `eq_count_100km_m2.5`: the query has no `limit`, and the FDSN service rejects requests that match over 20000 events with HTTP 400 (https://earthquake.usgs.gov/fdsnws/event/1/, parameter `limit`). An AOI near a very active region would fail instead of returning a count. The example value is 0.0 (float) though the unit is count.
- USGS `eq_max_mag_100km`: the example is empty (no events). The maximum mixes magnitude types (magType varies per event). SI_unit "1" is a dimensionless magnitude.
- `sources.tsv` calls `usgs_fdsn` and `eccc_naps` "fixed sensor", yet `usgs_fdsn` is an event catalogue; `eccc_ghgrp` and `eccc_npri` are facility self-reports ("survey").
- The NAPS Means header (https://data-donnees.az.ec.gc.ca/api/file?path=...2024_Means_EN.csv) is reachable only through the `api/file` redirect; the `/data/...` browse URLs return an HTML app shell, so file links must use the api form.

## infrastructure


- ovt_region_code has SI_unit "count" (feature_units.tsv / in/infrastructure.tsv) but the value is an ISO 3166-2 string such as CA-AB. Unit should be blank.
- ovt_control_infra_rows is emitted by four adapters (overture_power, overture_power_plant, overture_communication, overture_utility; adapters_infrastructure.py:422,437,466,500,761) under one key, so the dataset column holds a single value for four different sources. Rows are duplicated in the input tsv.
- ovt_substation_n_aoi (adapters_infrastructure.py:513) and ovt_power_substation_n (:483) are the same class=substation count from the same table (example 59 for both). Likewise ovt_power_plant_present and ovt_comm_tower_present are derived flags with names broader or narrower than their rule (comm_tower_present is true for any communication-subtype feature, :769; power_plant_present counts generators too, :514).
- ovt_power_plant_named (:515-517) takes the first name among plant, generator AND substation rows, so it can be a substation's name.
- ovt_extractive_area_km2 (:604) sums class quarry + landfill; landfill is not extraction (OSM landuse=landfill: "Place where waste is dumped."). Example 450.277 = quarry 445.47 + landfill 4.807.
- ovt_industrial_area_km2 / _frac / _n (:579-580,600-603) are a union of 12 classes (industrial, quarry, brownfield, landfill, military, railway, commercial, retail, construction, port, harbour, depot), not Overture class=industrial. The name misleads; example 496 km2 vs ovt_landuse_km2_industrial 32 km2.
- ovt_opencellid_status (:761) is a hard-coded constant "auth-blocked-401"; the code never calls OpenCelliD (docstring :751-755), so it is not a probe result.
- ovt_building_footprint_skipped_n (:744) holds the full in-AOI building count n (written when n > 60000), not a count of skipped buildings. Example 70621.
- ovt_building_mean_footprint_m2 (:742) divides clipped-footprint area by n, where n counts bbox-centre-in-AOI buildings, so numerator and denominator use different membership tests.
- nrcan900a_nearest_commodity reads PRD_DESC_E (adapters_physical.py:678); in the 75th-edition dbf PRD_DESC_E holds the commodity (e.g. "Gold") while PRODUCT_E holds the product group ("Precious metals"). The geoquery name is right, but no upstream data dictionary defines either field (shapefile zip has no metadata file; REST layer 3 uses different names operation_name_en / product_en_spelt).
- nrcan900a_total_records is the layer row count (183), constant for every AOI; not an AOI feature.
- osm_building_per_km2 (pipeline.py:434) divides a count made over the AOI bbox (pipeline.py:428-429) by the AOI polygon area_km2 (counts are not clipped to the polygon). If the AOI is not rectangular this overstates density. osm_highway_ways / osm_building_ways have the same bbox-vs-polygon mismatch. Overpass `out count` totals include only way[] so building nodes/relations are missed.
- ovt_*_n_bbox vs ovt_*_n: examples are equal (28777/28777, 25223/25223), so the AOI polygon equals its bbox here and the two features carry no distinct information in this dataset.
- ovt_control_building_rows = 41, ovt_control_segment_rows = 30, ovt_control_division_rows = 1, ovt_control_landuse_rows = 1 are non-zero for the mid-Pacific control bbox (:55), so the "control should be empty" premise does not hold; these are QA probes, not features.
- gppd_*: obs_date label says v1.3.0 (adapters_infrastructure.py:575) but the CSV is fetched from the unpinned master branch (:529-530). Also gppd_nearest_km is the minimum over all plants worldwide (no cap), so nearest_* may be hundreds of km away; gppd_median_commission_year_50km is a median of rounded years, and example 2010.0 is a float year.
- GPPD has no column-level data dictionary in WRI's repo README (https://github.com/wri/global-power-plant-database) or dataset page (https://datasets.wri.org/dataset/globalpowerplantdatabase); the capacity, commissioning-year and name quotes come from the Google Earth Engine catalog schema (https://developers.google.com/earth-engine/datasets/catalog/WRI_GPPD_power_plants), which uses different column names (capacitymw, comm_year, name). The EE comm_year wording ("weighted by unit-capacity") differs from other mirrors that describe commissioning_year as the first year of generation; unverified which applies to the CSV column.
- Overture's per-value class/subtype pages (infrastructure_class, infrastructure_subtype, land_use_class, building_class, most road_class and rail_class values) give no per-value descriptions. Where the brief allowed it I quoted the OSM wiki tag page instead, flagged in `note`; the Overture-class to OSM-tag mapping is not stated on the Overture pages I fetched.
- All quotes were retrieved through the WebFetch summariser, not byte-compared to the pages. A few (e.g. the ovt infrastructure intro, OSM power=plant) were returned in split fragments and rejoined as one sentence.
- Overture release is "latest in S3 listing, else 2026-09-23.1" (adapters_infrastructure.py:54,141); the dataset was built at an unrecorded release, so definitions are for the current docs, not necessarily the build's schema.
- SI_unit for counts of in-AOI features ("count") and ovt_max_place_population_radius ("count") is acceptable, but ovt_division_search_radius_km, ovt_landuse_km2_* use km/km2 and the code uses a local equirectangular approximation (:321-346), not geodesic.

## latent_spectral

- `aef_emb_tile_path` example value in in/latent.tsv is truncated (`...-0000008192.t`); the code writes the full `.tiff` path (adapters_embeddings.py:311).
- `aef_emb_l2_norm` (0.889) is the norm of an AOI mean of unit vectors, so it is <=1 by construction and measures within-AOI agreement. Upstream says per-pixel embeddings are unit length (https://developers.google.com/earth-engine/datasets/catalog/GOOGLE_SATELLITE_EMBEDDING_V1_ANNUAL); the name may mislead a reader into expecting 1. `aef_emb_l2_norm_pixel_mean` is the one that should be ~1.
- `aef_emb_component_std` and `clay_emb_component_std` are the std across the vector's components (adapters_embeddings.py:307, adapters_physical.py:360), not across pixels; the name suggests spatial variability.
- `aef_emb_pixel_count` counts pixels of a decimated read (<=160 px per side, adapters_embeddings.py:115), not native 10 m pixels; `aef_emb_n_tiles` is capped at 4 (MAX_TILES).
- `aef_emb_a00..a63` are AOI means of de-quantised bands, so they are not unit length and are "not independently interpretable" upstream; the SI_unit "1" is fine (upstream "Dimensionless").
- `clay_emb_mgrs_tile` is picked from the AOI centroid only (adapters_physical.py:336); the AOI mean is then taken within that one tile file, so an AOI spanning two MGRS tiles reflects one.
- `clay_emb_cos_to_tile_mean` compares against the mean of all rows in the file; Clay docs describe a separate "one average embedding per MGRS tile" (https://clay-foundation.github.io/model/clay-v0/model_embeddings.html). Not necessarily the same vector.
- `lst_c_*`: SI_unit degC is the geoquery conversion; upstream ST is Kelvin (https://www.usgs.gov/landsat-missions/landsat-collection-2-surface-temperature). Scene is a single least-cloudy scene, May-Sep 2024 (pipeline.py:203-206).
- `palsar_*`: adapter reads with `read_best(..., "HH")` over 2020-2025 items (pipeline.py:294-296), so the epoch varies per AOI. The 25 m DN formula quoted is from the Earth Engine yearly mosaic page; the JAXA PDF could not be fetched (EORC site down). Calibration-factor consistency of the Planetary Computer copy was not verified.
- `s1_vv_db_mean` takes only items[0] of an unsorted-by-orbit search (pipeline.py:310-316), so it is one scene, not a composite.
- `s2_*` use raw DN with no BOA_ADD_OFFSET handling (pipeline.py:187-199); `s2_red_reflect_mean` is DN/10000 only. Post-2022 L2A scenes carry a -1000 offset, so values are biased high (~+0.1 reflectance) for those scenes. Not checked against the STAC item's raster:bands.
- `s2_cloud_cover_pct` is the whole-scene eo:cloud_cover, not AOI cloud cover, and its example (0.080) is already a percent.
- `s2_ndvi_n_px` (55977) and `s2_ndwi_n_px` (55978) differ by one for the same AOI and scene, from independent masking.
- `s2sig_*` features are geoquery-computed. The code's own docstring says it "is NOT a learned embedding" (adapters_s2signature.py:11), yet the source is filed under slot "embeddings" in the dataset; the indices (`ndvi_med` etc.) are computed on quantile-matched grids rather than per pixel (adapters_s2signature.py:75-84), unlike `s2_ndvi_*`.
- `s2sig_raw_*` and `s2sig_w*` carry no offset correction either (adapters_s2signature.py:68). `s2sig_year` is always 2024 even where scenes fall back to 2023 (lines 43,134). `s2sig_version` has an empty SI_unit (string).
- `s2sig_w00..w29` names embed the sorted component name; index and name must stay in step with the alphabetical sort (adapters_s2signature.py:115,129).

## macrobiology


- hansen_loss_frac_2001_2024: name says 2001-2024 but the adapter reads GFC-2025-v1.13 (adapters_physical.py:69), whose lossyear spans 2001-2025; the example hansen_loss_last_year is 2025.0, which contradicts the name. https://storage.googleapis.com/earthenginepartners-hansen/GFC-2025-v1.13/download.html
- Hansen's own v1.13 page says lossyear is "a value in the range 1-20" while also saying "2001-2025" (that is 25 values); the upstream text is internally inconsistent. The GEE catalog page for v1.13 says 1-25.
- hansen_loss_n_years_affected has SI_unit `yr` but is a count of distinct years (adapters_physical.py:223); `count` fits better. hansen_loss_modal_year/last_year are calendar years, not durations, so `yr` as an SI unit is also doubtful.
- hansen_n_px and modis_n_composites have float example values (71360.0, 4.0) though the code returns int (adapters_physical.py:206, pipeline.py:333); hansen_loss_n_years_affected likewise (25.0).
- hansen_loss_modal_year is set to 0 when there is no loss (adapters_physical.py:226); 0 is not a year and sits in a `yr` column.
- hansen_gain_frac_2000_2012 is subtracted from a 2001-2025 loss fraction in hansen_net_change_frac (adapters_physical.py:238); the periods differ, and gain is treated as 0 when the gain tile is missing.
- agb_mgha_*: upstream HGB (Spawn et al. 2020) is biomass CARBON density in Mg C/ha, not Mg/ha of biomass (ORNL doc p.3, https://data.ornldaac.earthdata.nasa.gov/public/global_vegetation/Global_Maps_C_Density_2010/comp/Global_Maps_C_Density_2010.pdf). The ORNL doc also lists "Scaling: 0.1" and UInt16 type; the adapter applies no scale (pipeline.py:282, stats scale=1.0). I could not open the PC raster to check whether the PC copy is already scaled. Example mean 336.9 / p90 685 for a 68% tree-cover AOI looks high for boreal forest, which hints at an unapplied or wrong scale; verify.
- agb_mgha_*: PC asset 'aboveground' is titled only "Global above-ground biomass"; the link to the ORNL file aboveground_biomass_carbon_2010.tif rests on the matching dataset description.
- gbif_distinct_species: example value 1200 equals facetLimit=1200 (pipeline.py:373), so it is a cap, not a species count, for any AOI with more species. GBIF counts here use the AOI bbox rectangle, not the AOI polygon (pipeline.py:371), so gbif_* describe a larger area than other features.
- iolulc_built_frac duplicates iolulc_frac_built (adapters_census.py:901-904 computes the same quantity twice).
- iolulc_* fractions are over non-zero pixels but include the Clouds class (10); iolulc_n_classes counts clouds as a class.
- iolulc_frac_*: PC's collection page gives no class definitions; the definitions are from Esri's item page for the same Impact Observatory series (the Esri page lists years through 2025, the PC collection says 2017-2023).
- nrcanlc_frac_*: NRCan publishes no class-definition text I could reach; only labels are available (PC label:classes). geoquery label for code 5 drops "deciduous" (temperate_broadleaf) and for code 2 drops "taiga". The code-to-label pairing is geoquery's own NRC dict (pipeline.py:174), checked only against label order.
- nrcanlc_frac_urban example 0.1043 (and mixed 0.058) look high beside 0.5775 needleleaf for a mining AOI; no upstream cause found, just an observation.
- wc_* : adapter labels the product obs_date 2021 (v200); the PC collection also holds 2020 v100. read_best picks the newest date, so v200 is expected. No feature for class 95 (mangroves) in this dataset; fine for Canada.
- modis_ndvi_mean: pc_item(limit=40) returns the newest 40 items across all MODIS tiles that touch the AOI (sorted by datetime desc, pipeline.py:150-170); sampling every 6th item can mix tiles and dates unevenly, and `[::6]` of 40 gives at most 7 candidates, so "4 composites" are not a fixed 16-day spacing. The meta obs_date is hard-coded "2024" (pipeline.py:335).
- modis_ndvi_amplitude: spread of at most 4 irregularly spaced composites, not a seasonal amplitude.

## public_health_microbiology


- Feature names `ena_geolocated_samples_25km`, `mgnify_samples_25km` vs code: ENA and MGnify filter on the AOI bbox padded by 0.25 degrees per side, not a 25 km radius (pipeline.py:384-385, 405-406). Names mislead.
- `phacww_viral_load_latest` and `phacww_7day_avg_latest`: PHAC's published data dictionary (https://health-infobase.canada.ca/src/data/covidLive/wastewater/covid19-wastewater-data-dictionary-en.csv) describes a newer layout (w_avg, EpiWeek, weekstart) that does not match the CSV geoquery reads (Date, Location, region, measureid, fractionid, viral_load, seven_day_rolling_avg, pruid). viral_load has no sourced definition; the 7-day average quote is from the dashboard, not a column dictionary.
- adapters_health_env.py:996-997: the mean over rows on the latest Date mixes solid and liquid `fractionid` rows and sites; the README already notes solid fractions are often per gram, so "copies/mL" for the mean is doubtful. The mean is not population-weighted, unlike PHAC's own dashboard aggregate.
- adapters_health_env.py:999-1003: `phacww_7day_avg_p90_1yr` pools every site and fraction in the province; `phacww_latest_vs_1yr_p90` (SI_unit "1") is a ratio of those pooled values. The example 2024-06-23 latest date is stale relative to the live file today (open CSV still ends mid-2024).
- adapters_health_env.py:912-915: `rvdss_influenza_pct_positive` uses `str.contains("Influenza")`, which also matches the "Influenza A" and "Influenza B" rows (the file has virus values Influenza, Influenza A, Influenza B). The mean averages three overlapping series.
- adapters_health_env.py:907-910: `rvdss_tests_latest_week` and `rvdss_detections_latest_week` sum across all virus rows (also ADV, EV/RV, HCoV, HMPV, HPIV, subtypes). A specimen tested for several viruses is counted several times, and Influenza plus its subtypes are double-counted. Example 5523.0 and 252.0 are floats for counts.
- RVDSS dictionary (Data_Dictionary.xlsx, sheet DataDictionary_labdata) lists virus values COVID-19, Influenza, RSV and column labels 'Tests', 'Detections', 'Percent of tests positive'; the CSV uses SARS-CoV-2 and lowercase names plus undocumented `region`, `province`. `Jurisdiction` in the dictionary is the country, not the province. Dictionary text has the typo "positivie".
- `rvdss_week` example "2026-W44" is not zero-padded ISO (adapters_health_env.py:905); the file's week numbers run 35..46 in 2026 (a PHAC surveillance week, Sunday to Saturday).
- adapters_census.py:250 docstring says ODHF has "9 039 rows" and :1076 "7 543 geocoded", but the metadata says v1.1 has 7,033 records and v1.0 about 2,000 more; the file fetched is `odhf_bdoes_v1.csv` while the provenance string says "v1.1" (:1104). Version is ambiguous.

- `odhf_n_*` features: ODHF documents coordinates only as "Latitude"/"Longitude" and warns "no guarantees are implied" on accuracy (https://www.statcan.gc.ca/en/lode/databases/odhf/metadata, section 5); distances inherit that.
- `odhf_nearest_*_km` and `odhf_n_*_within_25km` for a type are emitted only if that type exists in the file (adapters_census.py:1100), so absence differs from zero.
- `mgnify_control_count` is a pipeline self-check (fixed mid-Pacific box), not an observation of the AOI; consider excluding it from the delivered dictionary or flagging it as a diagnostic (pipeline.py:388-392).

## socio_economic


- statcan_csd_pop_2016, statcan_csd_households_2016, statcan_csd_land_area_km2 and statcan_csd_med_hh_income_cad are area-weighted MEANS across every CSD the AOI touches (adapters_census.py:608-623), not the CSD's own count. A blended "median" is not a median, and a blended count is not a population or household count. The names read as the census values. Same for statcan_avg_dwelling_value_cad (adapters_census.py:1026).
- statcan_owner_occupied_dwellings is a plain SUM of whole-CSD totals (adapters_census.py:1027), while its sibling statcan_avg_dwelling_value_cad is area-weighted. An AOI touching a large CSD edge gets that CSD's full owner-dwelling count.
- statcan_csd_pop_density_km2 is recomputed from POP_2016_EN / LAND_AREA_EN (adapters_census.py:608-611). With water excluded from LAND_AREA this is persons per km2 of land, so it is not comparable to ghspop_density_km2, which divides by AOI total area (adapters_census.py:790).
- statcan_wds_popest reads cube 17-10-0155 "2021 boundaries" (WDS getCubeMetadata cubeTitleEn) but looks up the CSDUID taken from the 2016 CSD layer (adapters_census.py:659-667). A CSD whose code changed between 2016 and 2021 either misses (province fallback, statcan_popest_geo_level=province) or matches a different unit.
- statcan_popest_latest for ref period 2025-07-01 is a "preliminary postcensal" estimate per cube footnote 4 (getCubeMetadata productId 17100155). The feature name says only "latest".
- statcan_popest_yoy_pct uses the previous returned data point, not necessarily the point one year earlier (adapters_census.py:684,690-692).
- statcan_popest_ref_period SI_unit is "date"; value is a plain YYYY-MM-DD string.
- statcan_ct_uid takes the string "none (outside any census tract / CMA)" as a value (adapters_census.py:635), mixing a sentinel into an ID column. statcan_cma_name/uid are filled for census agglomerations as well as CMAs (e.g. Wood Buffalo CA, uid 860); the "cma" name follows StatCan's combined CMA/CA field (Boundary Files Reference Guide, Table 4.12).
- statcan_aoi_area_km2 and ghspop_density_km2 divide by the same AOI area (4350.567 km2 implied by example 84660.1 / 19.46); duplicate information across sources.
- ghs_smod labels: geoquery's ghssmod_dominant_label and frac_* names ("very dispersed rural", "dispersed rural", "dense_town", "semi_dense_town") differ from GHSL's own class names ("Very low density rural grid cell", "Low Density Rural grid cell", "Dense Urban Cluster", "Semi-dense Urban Cluster"), adapters_census.py:811-816 vs GHSL_Data_Package_2023.pdf PDF p.56-57. "Town" is not a GHSL term.
- ghssmod_is_urban counts class 21 (suburban/peri-urban) as urban (urban = classes >= 21, adapters_census.py:868), a geoquery rule not in GHSL.
- Example ghssmod_frac_* values sum to 1.0056 (0.0007+0.0053+0.0055+0.0009+0.0048+0.0034+0.9742+0.0108); either the examples come from different AOIs or fractions were rounded inconsistently. Individual 4-decimal rounding cannot explain +0.0056.
- ghspop_* unit: GHSL Data Package Table 19 (PDF p.53) labels the product "Population density" with "Values are expressed as decimals", while section 2.5 (PDF p.50) says the grid is "expressed as the number of people per cell". The adapter treats cells as person counts (sum = total persons), consistent with the section text and with example totals; SI_unit "count" is right but the table label is contradictory.
- ghspop_cell_p90 and ghspop_cell_mean are statistics of the 3 arcsec (~100 m) cells, so they scale with latitude (cell area varies with cos(lat)); not persons per km2.
- alta_* docs are GeoBase Aboriginal Lands Edition 1.1 (2010). The adapter reads per-province CLSS shapefiles (AL_TA_<prov>_SHP_DCM_eng, adapters_census.py:216-238) whose attributes may differ from the 2010 catalogue; Open Canada notes "some attribute differences" between the web service and the downloadable data (https://open.canada.ca/data/en/dataset/522b07b9-78e2-4819-b736-ad9208eb1067).
- Example alta_nearest_name KAWAWACHIKAMACH (a Quebec Naskapi community) with alta_province_extract AB: the examples are evidently from different AOIs, or the adapter's multi-province nearest search crosses extracts. Both should be checked on a single AOI.
- alta_overlap_km2 is computed in EPSG:6933 on the CSD-style clip (adapters_census.py:99-105); alta_overlap_frac uses the same. Fine, but note 57.25761 km2 / 4350.567 = 0.01316 (consistent).
- qc_assessment_catalogue_hits is a count of CKAN catalogue records matching the text "role evaluation fonciere" (adapters_census.py:1054-1061), not a count of assessment records or properties. The example value 5 equals the rows=5 request parameter, which package_search does not use for count; worth confirming it is not a truncation artefact. qc_assessment_source_host is a provenance string rather than a measurement.
- StatCan HTML documentation (www12.statcan.gc.ca, www150.statcan.gc.ca/n1 and /t1/tbl1) returns HTTP 403 "Security Check" to automated clients. Definitions were taken from: a university-hosted copy of the 2016 Census Dictionary PDF (cat. 98-301-X2016001), the Boundary Files Reference Guide on ftp.maps.canada.ca, the layer descriptions of the StatCan REST map service, and the WDS API itself (cube metadata and user guide on www.statcan.gc.ca). A collaborator may prefer official www12 URLs: https://www12.statcan.gc.ca/census-recensement/2016/ref/dict/pop123-eng.cfm (Total income), https://www12.statcan.gc.ca/census-recensement/2016/ref/dict/geo012-eng.cfm (CSD); these were listed by Open Canada but not fetched.
- Wikidata (wd_*) counts bbox, not AOI polygon, and an entity with several P31 values counts under each class, so wd_top5_class_share is an upper bound and can be capped at 1.0 (adapters_infrastructure.py:865).
- No definition could be found for statcan_csd_pop_2016, statcan_csd_name and statcan_province beyond the map service's field labels; the 2016 Dictionary has no standalone population-count entry.
